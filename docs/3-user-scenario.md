## 1. 개요

### 목적

본 문서는 C-MAKER의 실제 화면·배치 흐름을 개발/QA 관점에서 검증하기 위한 사용 흐름 시나리오(user flow scenario)를 정의한다. 각 시나리오는 "사용자 행동 → 시스템 응답"의 단계별 흐름으로 기술하며, 정상 흐름뿐 아니라 도메인 정의서에 정의된 주요 오류·예외 흐름도 포함한다.

> 시나리오 등장인물은 역할별 최소 인원(RM 김도윤, 지점장 한서영, 본부 마케팅 최유나, 본부 준법감시 박지훈)으로 한정하며, 마케팅용 페르소나 카드(연령·목표·페인포인트 등)는 다루지 않는다.

### 참조 문서

| 문서 | 버전 | 비고 |
|---|---|---|
| `1-domain-definition.md` | v1.4.0 | 요구사항(REQ-01~17), 엔티티, 유효성 제약(VAL-01~12), 도메인 규칙(RULE-SENSE/TARGET/BRIEF/LEARN/CAMPAIGN), 핵심 계산값 정의, 유스케이스(UC-01~18) 및 인수 기준 |
| `2-prd.md` | v1.4.0 | 목표 사용자, 비즈니스 목표, 제품 범위와 우선순위, 데이터 소스, 일정 |
| `report/CHANGE-REQUEST_v1.md` | — | REQ-16·UC-17 신설, REQ-02 재정의 근거 |
| `report/db-schema-decisions-review.md` | — | UC-01·UC-02(지점 등록/수정 화면) MVP 스코프 제외, 이력 테이블 구현 방식 근거 |

### 작성 원칙

- UC-01~18 전체를 커버하되, 실제 화면·배치 흐름 단위로 9개 시나리오로 묶어서 정리한다.
- 시스템 단독 배치(UC-03/04/05/10)는 별도 시나리오로 분리하지 않고, 그 결과를 사람이 확인하는 시나리오의 배경 흐름으로 포함한다.
- 각 시나리오는 정상 흐름을 우선 기술하고, 도메인 정의서에 정의된 오류·제약 케이스를 예외 흐름으로 최소 1개 이상 포함한다.

## 3. 시나리오별 상세

### SC-01. 지점 등록 및 담당 상권 설정(운영자 DB 직접 입력)

**등장인물**: 운영자 (신규 지점 온보딩)
**관련 UC**: UC-01(지점 정보 등록), UC-02(지점 정보 수정) — **화면·API 없음, MVP 스코프 제외**(`report/db-schema-decisions-review.md`)
**관련 REQ**: REQ-01

#### 정상 흐름

| # | 운영자 행동 | 시스템 응답 |
|---|---|---|
| 1 | 운영자가 psql로 `BRANCH`에 지점코드, 지점명, 도로명주소, 담당 상권 반경, 주력 업종, 외화 취급 여부, ATM 대수를 INSERT한다 | 지점코드 유일성·형식(숫자 6자리, VAL-01)과 반경 범위(0.5~3.0km, VAL-02)를 DB `CHECK` 제약으로 검증한다. 좌표(lat/lng)는 NULL로 남는다 |
| 2 | (배경) 별도 지오코딩 배치(10분 주기)가 주소로 좌표를 조회해 채운다 | `BRANCH.lat/lng`가 채워진다(RULE-BRANCH-03). 실패해도 지점 저장 자체는 영향받지 않는다(VAL-03 폐기) |
| 3 | 운영자가 이후 지점 정보(예: 담당 상권 반경)를 UPDATE한다 | INSERT/UPDATE 트리거가 변경 전 값을 `BRANCH_HISTORY`로 옮기고 `BRANCH.effective_from`을 다음 날 07:30으로 자동 설정한다(RULE-BRANCH-01, CONST-19). 일간 배치는 `effective_from` 이전까지 `BRANCH_HISTORY`의 옛 값을 사용한다 |

#### 예외 흐름

| # | 운영자 행동 | 시스템 응답 |
|---|---|---|
| 4 | 운영자가 이미 등록된 지점코드로 신규 INSERT를 시도한다 | DB `UNIQUE` 제약(CONST-01)이 거부한다. 기존 레코드는 UPDATE로 처리한다(RULE-BRANCH-02) |
| 5 | 지오코딩 배치가 존재하지 않는 주소에 대해 계속 실패한다 | 재시도·알림 로직이 없으므로 좌표는 NULL 또는 옛 값으로 남는다. 이 리스크는 감수하는 것으로 결정되었다(`report/db-schema-decisions-review.md` §5) |

### SC-02. 아침 배치 결과로 오늘의 접촉 목록 확인

**등장인물**: RM 김도윤 (영업점 담당자)
**관련 UC**: UC-17(모집단 적재, 배경), UC-03(사업자 상태 검증, 배경), UC-04(일간 신호 배치, 배경), UC-06(TOP 20 조회), UC-07(브리프 상세 조회)
**관련 REQ**: REQ-16, REQ-02, REQ-03, REQ-05, REQ-06

#### 정상 흐름

| # | 사용자 행동 | 시스템 응답 |
|---|---|---|
| 0 | (배경) 매월 1회 인허가 전수 자료로 담당 상권 내 사업체 모집단이 갱신되어 있다(UC-17) | 일간 배치는 이 모집단(BUSINESS)을 대상으로 실행되며, 모집단 적재 자체는 일간 07:30 SLA 대상이 아니다 |
| 1 | (배경) 매일 07:00경 배치가 실행된다 | 인허가 영업상태(D-2 기준)로 휴·폐업 사업체를 1차 배제하고, 사업자번호가 확보된 사업체에 한해 국세청 상태조회로 2차 보완 확인한다(UC-03, REQ-02). 인허가·거시·기상·재난 신호를 수집해 임계치 초과분을 이벤트로 승격한다(UC-04, RULE-SENSE-03) |
| 2 | (배경, 계속) | 배제 필터(RULE-TARGET-01)를 통과한 사업체를 스코어링(신선도 항 포함, RULE-TARGET-02/05)하여 지점별 TOP 20(그중 3건은 탐색 슬롯, RULE-TARGET-03)을 확정하고 07:30 이전 브리프 생성을 완료한다 |
| 3 | 김도윤이 07:35 대시보드에 접속한다 | 김도윤 소속 지점의 오늘의 접촉 TOP 20을 점수순으로 표시하며, 각 항목에 선정 사유 1줄을 함께 보여준다 |
| 4 | 김도윤이 특정 항목을 열어 상세 브리프를 확인한다 | 전화 화법·방문 체크리스트를 표시하고, 모든 사실 문장에 출처 태그(`[소스명 · 기준일]`)를 붙인다(RULE-BRIEF-01) |

#### 예외 흐름

| # | 사용자 행동 | 시스템 응답 |
|---|---|---|
| 5 | 김도윤이 목록에서 폐업 처리된 사업체가 있는지 확인한다 | 인허가 영업상태로 휴·폐업이 확인되었거나(1차), 사업자번호가 있어 국세청 조회로 재확인된(2차) 사업체는 배제 필터에서 이미 제외되어 목록에 노출되지 않는다(RULE-TARGET-01) |
| 6 | 김도윤이 근거 없는 문장이 있는지 브리프를 검토한다 | 도구 조회 결과에 근거가 없는 문장은 생성 단계에서 이미 차단되어 있으며, 해당 항목은 사유만 표시된다(RULE-BRIEF-02) |
