- **작성일**: 2026-09-08
- **상태**: 검토만 완료, 공식 문서(`1-domain-definition.md`, `6-erd.md` 등) 미반영
- **목적**: USER/BRANCH 테이블 운영 방식 변경에 대해 논의한 결정 사항을 한 곳에 모아, 추후 공식 문서에 반영할 때 참고한다.

## 1. USER 테이블

| 항목 | 결정 |
|---|---|
| 계정 생성 방식 | 운영자가 psql로 직접 INSERT. 별도 가입 서비스/화면 구현 안 함 |
| 비밀번호 저장 | 평문 저장. 해싱 미적용 |
| 컬럼명 | `password_hash` → `password`로 변경 (평문 저장에 맞춤) |
| 계정 등록 기능 | F-0 "담당자 계정 등록" 요구사항 스코프 제외 |

## 2. BRANCH 테이블

| 항목 | 결정 |
|---|---|
| 데이터 입력 방식 | 운영자가 psql로 직접 INSERT/UPDATE (등록·수정 API/화면 없음) |
| 직접 입력 컬럼 | branch_code, name, address, handles_forex, atm_count, coverage_radius_km, primary_industry_tags |
| 자동 처리 컬럼 | lat, lng (4번 참조), effective_from (3번 참조) |
| branch_code 형식 | 숫자 6자리 (`CHECK (branch_code ~ '^[0-9]{6}$')`) |
| 지점 등록/수정 UI | UC-01, UC-02, `BranchSetupPage`, API-01 스코프 제외 |

## 3. RULE-BRANCH-01 (익일 반영) 처리 방식

- **규칙 자체는 유지**: "지점 정보 변경은 다음 날 07:30 배치부터 반영"
- **구현 방식**: 히스토리 테이블 방식 ((a) 신규만 지연 적용 vs (b) 히스토리 테이블 중 (b) 선택)
  - 값 변경 시 옛 값을 별도 히스토리 테이블에 보관
  - `effective_from`을 트리거로 "다음 날 07:30"으로 자동 갱신 (INSERT + UPDATE 양쪽 트리거 필요)
  - F-1 배치는 `effective_from <= 오늘 07:30`인 값만 사용, 그 전까지는 히스토리의 옛 값 사용
- **07:30 F-1 배치 자체(외부 데이터 소스 신호 감지)는 그대로 유지** — 수동 트리거 방식으로 바꾸지 않음

## 4. lat/lng (지오코딩)

| 항목 | 결정 |
|---|---|
| 채우는 방식 | 별도 배치 잡, DB 트리거 아님 (외부 API 호출이라 트리거 부적합) |
| 실행 주기 | 10분마다 |
| F-1과의 순서 보장 | 없음 (별도 로직 없음) |
| 히스토리 처리 | coverage_radius_km 등 다른 설정값과 동일하게 히스토리 테이블 대상에 포함 — 즉 주소가 바뀌어도 옛 좌표를 유지하다가 effective_from 시점에 새 좌표로 전환. **자동 NULL 처리 트리거는 이걸로 대체(폐기)** |
| nullable 여부 | lat, lng 컬럼은 nullable로 유지 |

## 5. 지오코딩 실패 처리

- **대응 로직 없음**: 재시도, 알림, 모니터링, 영구 실패 감지 등 어떤 것도 구현하지 않음
- 리스크(주소 변경 후 지오코딩이 계속 실패하면 옛 좌표가 새 주소에 남아 틀린 위치로 남을 수 있음)는 감수하는 것으로 확정

## 6. DB 유효성 검증

- **범위**: 단일 행(VAL-01, 02, 04, 05, 06, 08, 09, 10) 제약만 DB CHECK로 구현
- **제외 범위**: 여러 행 집계 제약(CONST-04, 06, 09, 11 — 지점당 이벤트 상한, 탐색슬롯 3건, 표본수 30 기준, 캠페인 다단계 승인 등)은 CHECK로 구현 안 함, 애플리케이션/배치 로직으로 남음
- VAL-03(지오코딩 성공 필수, 실패 시 저장 불가)은 사실상 폐기 대상 — 비동기 배치로 전환했으므로 저장 시점에 이 제약을 걸 수 없음
